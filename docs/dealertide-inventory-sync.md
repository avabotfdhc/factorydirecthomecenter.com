# DealerTide inventory → staging → catalogue

DealerTide (Oct 9, 2026) asked us to re-import their inventory feed: 241 homes, now
linked to Champion catalog models, with photos on 199 and floor plans on 202, and the
12 Champion Genesis homes removed. The website had never imported it — its homes come
from the Supabase catalogue built from Champion's Box library — so Kyle chose to **add
to the current catalogue without duplicates or disturbing it, after checking the
photos and floor plans against what we already have.**

That is two steps, and only the first one exists so far.

## Step 1 — stage and compare (built)

Nothing in this step touches a table the website reads.

| Piece | What it does |
|---|---|
| `supabase/functions/dealertide-sync` | Edge function. Pulls every page of `GET https://api.dealertide.com/public/inventory?token=…&statuses=available,available_to_order&per_page=50&page=N` until `meta.total_pages`, matches homes on `id`, upserts them into `dealertide_inventory`, flags any home whose `image_urls` / `floor_plan_images` list changed (`media_changed_at` — photos change without `updated_at`), and marks a home removed only when it has left the list **and** its detail call answers 410. Writes a row to `dealertide_sync_runs` each time. |
| `public.dealertide_inventory` | One row per DealerTide home: Champion `model_code` parsed from the record, the two URL lists, the raw record. Private (RLS, no grants). |
| `public.dealertide_catalogue_match` | View: each live DealerTide home against the catalogue. `match` is `in_catalogue`, `retired_series_only` (only a Paramount plan has the model), `new_model` or `no_model_code`, with `their_photos` / `their_floor_plans` beside `our_photos` / `our_drawings` / `our_sheets`. Several DealerTide homes can share a model; they all point at the same plan. |
| `public.dealertide_sync_start()` | Starts a sync from SQL via `pg_net`. The function's JSON summary lands in `net._http_response`. |

The sandbox cannot reach `api.dealertide.com` or Supabase's function URLs (403 at the
egress proxy), which is why the pull runs inside Supabase and is started from SQL.

### Secrets

- `DEALERTIDE_INVENTORY_TOKEN` — Supabase → Edge Functions → Secrets. Kyle enters it;
  it is never in the repo, chat or logs (it rides in DealerTide's URL, so the function
  never logs or returns a URL).
- `dealertide_sync_key` — generated by the migration into the Supabase vault. The
  function is deployed with `verify_jwt` off and admits only a request whose
  `x-sync-key` matches it (`dealertide_sync_key_ok()`); `dealertide_sync_start()` sends it.

### Running it

```sql
select public.dealertide_sync_start();             -- returns a request id
select status_code, content from net._http_response order by id desc limit 1;
select match, count(*) from public.dealertide_catalogue_match group by 1;
```

The summary includes `sample_fields` (field names only) so the model-code parser can be
adjusted to DealerTide's real record shape; `with_model_code` says how many it parsed.

### Running it from the website instead (2026-10-18)

The edge function's secret was never set — Kyle keeps every key on Vercel, and
the agent session cannot read Vercel env vars to move it — so the same sync now
also runs on the site: `POST /api/dealertide/sync`
(`src/lib/dealertide-inventory-sync.ts`) reads the token from
`DEALERTIDE_INVENTORY_TOKEN`, or the `token=` inside `DEALERTIDE_FEED_URL` (the
feed URL the site has carried since August), and writes the same two tables
with the service role. The gate is the same `x-sync-key` / vault check.
`/api/health` → `configured.dealerTideInventoryToken` says whether a token is
present, and `dealerTide.envNames` lists the DealerTide-related variable
**names** (never values) the deployment carries, so a token pasted under an
unexpected name can be found. `inventoryToken()` accepts the usual names
(`DEALERTIDE_INVENTORY_TOKEN`, `…_INVENTORY_KEY`, `…_FEED_TOKEN`,
`…_TOKEN`, or any of them holding the full feed URL), **case-insensitively**,
plus any other `DEALERTIDE*` variable whose value is a feed URL with
`?token=`; never `DEALERTIDE_API_KEY` or anything named for leads. Measured
on 2026-10-18, production's names are `DEALERTIDE_API_KEY`,
`Dealertide_Inventory_Key` (the inventory token, mixed case),
`DEALERTIDE_FEED_UR` (the feed URL, last letter missing, which is why the
feed adapter never saw it) and `Dealertide_website_leads`.

```sql
select public.dealertide_sync_start_site();        -- returns a request id
select status_code, content from net._http_response order by id desc limit 1;
```

Either path leaves identical rows, so the comparison view below does not care
which one ran.

## What the first real sync found (2026-10-18)

242 homes on 5 pages, all `available_to_order`, three makes (Champion, Champion
Homes, Dutch Housing). The Champion model code is the feed's `identifier`
field (`2852H32A1C`), the family name is `model` and the series is `trim`;
the first parser read none of those, so the staged rows were patched in SQL and
the parser fixed. Against the catalogue:

| match | homes | with photos | with drawings |
|---|---|---|---|
| `in_catalogue` (167 distinct plans) | 169 | 97 | 136 |
| `no_model_code` | 73 | 73 | 73 |
| `new_model` / `retired_series_only` | 0 | — | — |

- The 73 without a code are DealerTide's older May records (`identifier` is a
  stock number such as `MH-20260504-AF76E5`) named by family only — "2026 Dutch
  Housing Aspire Belvidere", "2027 Champion Homes Prime Somerset 043". A family
  name maps to several lengths (Warren 2852/2856/2860), so their media cannot be
  assigned to one plan from the feed alone. The Prime name match in the view
  found nothing because our Prime plans are mostly code-named.
- Image hosts: 957 URLs on Champion's Scene7 library (`s7d9.scene7.com`),
  264 on DealerTide's staging S3 bucket, 63 on our retired
  `factory-direct-homescenter` S3 bucket. Only Scene7 is copied.
- Of the 19 active plans with no photo at all (13 Aspire 32'-wide twins, 6
  Prime), the feed had photos for exactly four: Verona 3276H/M42179 (4 real
  Verona photos, incl. an exterior) and Woodward 2864H/M32047 (Champion's 4
  staged interiors of the **2860** Woodward, which Champion itself attaches to
  the 2864 listing; the filenames say 2860). All 16 were imported (below).
  Henderson and Madison get nothing; the feed has no codes for the six Prime.
- Wider gap, **not acted on**: 51 in-catalogue plans where the feed has more
  photos than we show (feed 583 photos total vs our 589), and 125 plans where
  the feed has a plan drawing and our row set has no `floorplan` image (we
  hold the sales sheets as documents instead). Both need a per-plan look,
  because the same Scene7 asset may already be in the bucket under a Box
  filename, and a `floorplan` row changes which drawing the page picks.

## Step 2 — add to the catalogue (`dealertide-media-import`)

Edge function `dealertide-media-import` (source in
`supabase/functions/dealertide-media-import/index.ts`), started from SQL:

```sql
select public.dealertide_media_import('{"slugs":["aspire-verona-3276h42179"],"dry_run":true}'::jsonb);
select status_code, content from net._http_response order by id desc limit 1;
```

Per named plan it finds the staged homes with the plan's own model code, fetches
each Scene7 photo at 1800px, checks it is a JPEG and reads its pixel size from
the file (refusing anything under 1000px wide or 30 KB), uploads it to
`<series>/<MODEL>/photos/dealertide/<champion-filename>.jpg` and appends a
`kind = 'gallery'` row. It never adds a `floorplan` row, never reads a host
other than Scene7, skips a path already attached, and promotes the first
`exterior` photo to the card image only when the current banner is a rendered
sales sheet. `dry_run: true` reports exactly what a real run would do.

First run, 2026-10-18: 16 photos onto the four plans above, all 1800×1200,
187–436 KB; the two Verona pages now carry the exterior photo as their card
image, the Woodward 2864 pair keep the rendered sheet (the feed has no exterior
for them). `npm run image-audit` was run afterwards.

Rules it follows, from AGENTS.md:

- **Never a second page for a model we already have.** `in_catalogue` homes add nothing
  but, at most, missing media on the existing plan. `retired_series_only` homes go
  nowhere — Paramount is retired and 301s to Aspire or `/series/redman`.
- **Check what each image is before copying it.** Matching a count is not the goal
  (2026-09-28: 14 legacy banners of the wrong model and a sales sheet filed as a photo).
  New rows are `kind = 'gallery'`, appended after existing rows; a drawing is never a
  `gallery` photo; `path` is a storage key, never an absolute URL. Run
  `npm run image-audit` afterwards.
- **Copy media into the `floor-plans` bucket**, don't hotlink DealerTide's URLs.
- New-model pages get the usual title ladder, narrative, specs disclaimer and no prices.

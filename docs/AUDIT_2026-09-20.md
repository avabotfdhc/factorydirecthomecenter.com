# Site, SEO/AEO and CRO audit — factorydirecthomescenter.com

**Date:** 20 September 2026
**Scope:** `avabotfdhc/factorydirecthomecenter.com` (Next.js 16 / Vercel / Supabase), its
structured-data graph, its lead pipeline and its dependency surface.
**Method:** full read of the repository, a production build, the rendered HTML of all 87
prerendered pages, `npm audit` against the live registry, and a local run of the search and
lead endpoints.

## What could NOT be measured, and why

Be sceptical of any audit that hands you Core Web Vitals numbers it did not take. This one
did not take them. The agent sandbox's network policy answers 403 for every outbound host,
so there was **no Lighthouse run, no CrUX / PageSpeed Insights data, no live crawl, and no
check of whether the Facebook and Instagram URLs in `sameAs` resolve**. Every performance
finding below is therefore a *mechanism* found by reading the code — a forced synchronous
layout, a duplicated listener — not a measured millisecond. The first item on the checklist
at the end is to take the real measurements, because that is the only way to rank the
remaining performance work honestly.

Everything in the "Fixed" column was verified by building the site and reading the output.

## 2. Technical performance, Core Web Vitals and mobile-first

### What is already right — do not "fix" these

The asset pipeline is in good shape and several things a generic audit would flag are
already handled correctly:

- `next/image` everywhere that matters. The only raw `<img>` elements are the lightbox
  overlay (deliberate — it loads the full-resolution original *after* a click, so the
  optimiser is not in the path), an admin preview, and the Meta Pixel noscript beacon.
- AVIF and WebP are configured, with a 31-day `minimumCacheTTL` and a Supabase Storage
  `remotePatterns` entry.
- The homepage hero carries `priority`, so the LCP candidate is preloaded and never lazy.
- Galleries lazy-load with `sizes` matched to the grid columns.
- Analytics load with `strategy="lazyOnload"` **and** behind consent, honouring Global
  Privacy Control. Tag scripts are not in the critical path.
- Shipped images are served `immutable` for a year; HSTS, `X-Content-Type-Options`,
  `Referrer-Policy` and a `Permissions-Policy` are all set.
- `htmlLimitedBots` is extended so audit crawlers get `<title>`/`<meta>` in `<head>`.

### Fixed here

**Forced synchronous layout on every scroll tick (H3, H4).** Two unthrottled scroll
listeners, each reading `scrollHeight` per event. Now one listener, rAF-coalesced, that
unbinds itself once the 90% milestone fires:

```ts
// src/lib/analytics.tsx
const measure = () => {
  frame = 0;
  const scrollPercent = Math.round(
    ((window.scrollY + window.innerHeight) / document.documentElement.scrollHeight) * 100,
  );
  for (const depth of depths) {
    if (scrollPercent >= depth && !tracked.has(depth)) {
      tracked.add(depth);
      trackScrollDepth(depth);
    }
  }
  if (tracked.size === depths.length) window.removeEventListener("scroll", onScroll);
};

const onScroll = () => {
  if (frame) return;
  frame = window.requestAnimationFrame(measure);
};
```

**A dead parallax hook** (`useParallax`) that registered a scroll listener calling
`getBoundingClientRect()` on every event, and that no component ever imported, was removed
rather than repaired.

### Remaining, in priority order

1. **Take the measurements.** Run Lighthouse (mobile, throttled) against `/`,
   `/floor-plans`, a floor-plan detail page and `/locations/fort-wayne`, and open the Core
   Web Vitals report in Search Console for field data. Nothing below should be prioritised
   above what those say.

2. **Font weight budget.** The root layout loads Cormorant Garamond at five weights and
   Plus Jakarta Sans at five — ten font files, self-hosted and preloaded by `next/font`.
   Audit which weights the design system actually renders and drop the rest; each unused
   weight is a preloaded request competing with the LCP image.

3. **Virtual-tour facade (S4).** `plan.virtualTour` currently renders as a link with
   `target="_blank"`. Never embed the Matterport iframe directly — it is megabytes of
   WebGL and would wreck LCP and INP on every plan page. The right pattern is a poster
   image that swaps to the iframe on click, keeping the buyer on the page:

   ```tsx
   "use client";
   import { useState } from "react";
   import Image from "next/image";

   /** Matterport, loaded only when the buyer asks for it. The poster is a real
    *  <Image>, so it is optimised and lazy like every other gallery tile; the
    *  iframe — megabytes of WebGL — is never in the initial page at all. */
   export function TourFacade({ tourUrl, poster, alt }: { tourUrl: string; poster: string; alt: string }) {
     const [live, setLive] = useState(false);
     if (live) {
       return (
         <iframe
           src={`${tourUrl}&play=1`}
           title={alt}
           allow="xr-spatial-tracking; fullscreen"
           allowFullScreen
           loading="lazy"
           className="w-full aspect-video rounded-2xl border-0"
         />
       );
     }
     return (
       <button
         type="button"
         onClick={() => setLive(true)}
         aria-label={`Start the 3D virtual tour of ${alt}`}
         className="group relative block w-full aspect-video overflow-hidden rounded-2xl"
       >
         <Image src={poster} alt="" fill sizes="(max-width: 1024px) 100vw, 50vw" className="object-cover" />
         <span className="absolute inset-0 grid place-items-center bg-black/30 group-hover:bg-black/40 transition-colors">
           <span className="rounded-full bg-white/95 px-6 py-3 text-sm font-bold uppercase tracking-wider">
             ▶ 3D Virtual Tour
           </span>
         </span>
       </button>
     );
   }
   ```

   The same rule applies to the homepage video slot in `src/lib/home-video.ts` when Kyle
   fills it in: use `youtube-nocookie.com` behind a poster, never an autoloading embed.

4. **`revalidate` on the floor-plan detail page is 300 seconds.** That is a five-minute
   window in which a transient Supabase failure's degraded render is served to everyone
   (the `resilient-fetch` work of 2026-09-11 is what keeps that from being a 404). Nothing
   to change today, but if CMS edits do not need to appear within five minutes, a longer
   window plus `revalidatePath` from the admin save would cut both risk and origin load.

## 3. Organic SEO, coverage and AEO

### Structured data — measured before and after

Counted by parsing every `<script type="application/ld+json">` in all 87 prerendered pages
of a production build:

| Node | Before | After |
|---|---|---|
| Pages with a **duplicate** `BreadcrumbList` | 23 | **0** |
| `MobileHomeDealer`-typed business node | 0 | 105 |
| `CollectionPage` (series hubs) | 0 | 5 |
| `ContactPage` | 0 | 1 |
| County pages with any structured data | 0 | all |
| Article nodes missing `datePublished` | every blog post | 0 |

**Why not `AutoDealer`.** The brief asked for `AutoDealer` / `LocalBusiness` /
`RealEstateAgent`. `AutoDealer` is the wrong type and would do harm: it tells Google the
business sells cars, and Vehicle/Car rich results are a different eligibility path
entirely. schema.org defines `MobileHomeDealer` — "a mobile-home dealer" — for exactly this
business, and that is what was added. `RealEstateAgent` and `HomeAndConstructionBusiness`
stay, because the dealership genuinely sells homes *and* coordinates site work. The
reasoning is recorded in `src/lib/business.ts` so the next person does not "correct" it.

**Why floor-plan pages still publish no `Product`/`Offer`.** Google's product-snippet
rules require `offers`, `review` or `aggregateRating` on every `Product`. Prices are hidden
site-wide (`SHOW_PRICES` / `SHOW_SALE_PRICES` are off) and there are no real reviews, so a
`Product` node would have none of the three and would be flagged in Search Console. The
page publishes `SingleFamilyResidence` instead, which carries `floorSize`,
`numberOfBedrooms`, `numberOfBathroomsTotal` and the manufacturer, and requires no offer.
The existing code already re-enables `Product` automatically the moment a numeric price
exists. **This is the correct behaviour — leave it.** If Kyle ever wants product rich
results, the trigger is a decision to publish prices, not a code change.

### AEO — answer engines

`robots.ts` already allows `GPTBot`, `ClaudeBot`, `PerplexityBot` and `GoogleOther`, which
is the single most important AEO setting and is done.

The one thing genuinely missing was **measurement**, and it now ships. The attribution
module classifies referrals from ChatGPT, Perplexity, Claude, Gemini, Copilot, You.com and
Phind as `medium = 'ai'`, broken out from plain `referral`, and the reporting view buckets
them as `answer engine`. Lumped in with referrals they are invisible; separated, they are
the only direct evidence anyone gets that AEO is working:

```sql
select date_trunc('month', created_at) as month, count(*) as leads
from public.lead_attribution_report
where channel = 'answer engine'
group by 1 order by 1 desc;
```

One file was deleted: `src/lib/aeo.ts`, 283 lines of generic "AEO helper" functions
(`optimizeForVoiceSearch`, `createEEATContent`, `generateQuestionHeaders`) that **nothing
imported**. It was worse than dead weight — its name implied the site had an AEO
implementation, when the site's real answer-engine strength is the FAQ blocks, the guides
and the per-plan narratives in `plan-content.ts`.

### Programmatic regional architecture (S2) — the blueprint, deliberately not built

The brief asks for landing pages across IN, OH, MI, IL, WI and KY. **Do not build them as a
batch.** The repo's own rules already say why, in `AGENTS.md`: mass-produced pages that
differ only by place name are the doorway-page pattern in Google's spam policies, and the
downside is a manual action, not merely weak ranking. Six states of templated pages is
precisely that pattern.

The structure that works, and that this codebase is already set up for:

```
/locations/<state>                      ← new tier: state hub, honest about delivery reach
  /locations/<county>-county            ← src/lib/county-pages.ts (programmatic, 4 counties today)
    /locations/<city>                   ← CityLocationTemplate (hand-written local content)
/guides/zoning/<state>                  ← new: the genuinely state-specific asset
```

Three rules for expansion:

1. **One differentiating fact per page, or no page.** Every county page must carry
   something the others cannot: the actual permitting authority, the frost-depth
   requirement, whether the county allows HUD-code homes outside a park. `county-pages.ts`
   already has `zoningNote`, `frostDepth`, `milesFromTopeka` and `points` fields for this —
   the schema is right, it only has four rows.

2. **State-level zoning guides are the highest-value new content**, not city pages. "Can I
   put a manufactured home on my land in Ohio?" is a real, high-intent query with a real,
   researchable answer that differs by state. Six of those beat sixty city pages.

3. **Go outward from Auburn, honestly.** Delivery economics get worse with distance. A page
   for a Wisconsin city 400 miles away that implies the same service as Fort Wayne is a
   bounce and a wasted crawl. Cover Ohio and Michigan properly before Illinois, Wisconsin
   or Kentucky get anything.

Ordering by expected return: (1) state zoning guides for OH and MI; (2) county pages for
the remaining northeast-Indiana counties with real local data; (3) the two or three Ohio
and Michigan border counties the dealership actually delivers to; (4) everything else, only
if 1–3 earn their keep.

### Smaller SEO items still open

- `/privacy` and `/terms` have no breadcrumb. Google does not show breadcrumbs for legal
  pages; left alone on purpose.
- `sameAs` carries Facebook and Instagram URLs recovered from the old site's markup. They
  could not be fetched from this sandbox. **Kyle: open both once and confirm they resolve
  — a dead `sameAs` entry is worse than a missing one.**
- The Semrush "48 broken external links" finding is still unverified for the same reason.
  The external URLs the site cites are in `src/lib/citations.ts` and the guide pages.

## 4. Local SEO and GBP synergy

The on-page foundation is genuinely strong and the duplicate-entity discipline in
`src/lib/business.ts` is better than most dealership sites. NAP consistency is enforced by
construction: one source file, one `@id`, and a test that fails if any business-typed node
carries a different one. That test now also covers `Organization`-typed namesakes, which is
how the blog's duplicate publisher had been slipping through.

What remains is **off-page and is Kyle's to do** — no amount of code changes it:

1. **Reviews are the gap, and they are a real one.** `src/lib/reviews.ts` is empty on
   purpose: the old testimonials were invented and were removed in September. That was the
   right call — fake reviews breach Google's fake-engagement policy and the FTC endorsement
   rule. But review count and velocity are among the strongest Map Pack factors, and the
   dealership currently publishes none. **Ask every closed buyer for a Google review.**
   The code path already exists: add real rows to `reviews.ts` (verbatim, named, dated,
   linked) and the homepage section switches back to quotes and starts publishing an
   `AggregateRating` automatically.

2. **GBP hygiene.** Confirm the pin drops on the showroom at 1211 IN SR-8 and not on the
   road; confirm hours match `business.ts` (Mon–Fri 9–5, Sat 10–4) including holidays; add
   products/services for each series; post weekly — new arrivals, a delivered home, a
   factory photo. GBP posts are the cheapest local ranking input there is.

3. **Citations.** NAP must be byte-identical on Bing Places, Apple Business Connect, Yelp,
   the Champion dealer locator and the manufactured-housing directories. "1211 State Road
   8" and "1211 IN-8" are different strings to an aggregator.

4. **Driving directions.** `BUSINESS.hasMap` is already a directions deep link rather than
   a map pin, which is the right choice — it opens navigation in one tap on a phone.

## 5. UX, merchandising and CRO

### Already right

Sticky mobile action bar (Call / Text / Quote) with real `tel:` and `sms:` links and a
pre-filled SMS body; an instant-quote modal instead of a bounce to `/contact-us`; an exit
intent popup; a compare tray; a delivery checker; a payment calculator; per-plan narratives
and FAQs; a lightbox with pinch-zoom, swipe and back-button handling. This is a
better-merchandised dealership site than most.

### S1 — the floor-plan page asks for six things at once

The CTA row renders, side by side: **Design This Home**, **Get a Quote**, **Call**,
**3D Virtual Tour**, **Floor Plan (PDF)**, **Download brochure (PDF)**. Only the first is
visually primary; the rest are near-identical outlined buttons. Six choices of similar
weight is choice paralysis, and three of them (tour, PDF, brochure) lead *away* from the
form.

The change to test — and it is worth an A/B test rather than a guess:

- **One primary action.** Pick it by what actually closes: "Get My Price" beats "Design
  This Home" for a first-time visitor, because it is the thing they came for.
- **Demote the assets.** Tour, floor-plan PDF and brochure become a quiet row of text
  links under the CTA, not buttons competing with it.
- **Gate nothing that is already public**, but do put the brochure email form *after* the
  download starts, not before it. `EmailBrochureForm` already exists; the question is
  ordering.
- **Keep "Call" prominent on mobile only.** On desktop it is dead weight; the sticky bar
  already carries it on phones.

### Forms

`useAntiSpam` turned out to be the ideal integration point — extending that one hook gave
all seven form components Turnstile without touching any of them. Worth remembering for the
next cross-cutting form change.

Still worth doing: the contact form asks for everything at once. Progressive disclosure —
name and phone first, then interest, timeframe, land status — reliably lifts completion on
long forms. Ask for the qualification fields *after* the contact details are captured, so a
drop-off still leaves you a lead.

## 6. CMS, CRM and inventory architecture

### C3 — the attribution pipeline (shipped)

This was the largest gap in the whole audit. Nine lead entry points, zero acquisition data.

**The design decision that matters:** attribution is captured once into a **first-party
cookie** and read on the **server** at submit time. It is not a form field.

- One cookie, not nine hidden inputs. The browser sends it with every POST, so every
  current lead path — and the tenth one someone adds next year — inherits attribution with
  no work.
- A scripted POST cannot forge a campaign into the CRM, because the value does not come
  from the request body.
- The server action forwards **only** that cookie to the internal `/api/leads` fan-out.
  Forwarding the visitor's whole `Cookie` header would hand an admin session to an internal
  fetch for no reason.

**First touch and last touch, both.** Manufactured-home buying runs weeks to months. A
last-touch-only model credits every sale to a branded search and hides the blog post that
actually found the buyer. The merge rule is the load-bearing part:

```ts
// src/lib/attribution.ts
export function mergeAttribution(existing: Attribution | null, touch: Touch): Attribution {
  if (!existing) {
    return { v: 1, first: touch, last: touch, visits: isAttributedTouch(touch) ? 1 : 0 };
  }
  if (!isAttributedTouch(touch)) return existing;   // ← a direct return never overwrites an ad
  const sameOrigin =
    existing.last.source === touch.source &&
    existing.last.medium === touch.medium &&
    existing.last.campaign === touch.campaign &&
    existing.last.clickId === touch.clickId;
  if (sameOrigin) return existing;
  return { v: 1, first: existing.first, last: touch, visits: existing.visits + 1 };
}
```

Get that one rule wrong and every lead is relabelled "direct" at the moment it converts,
which is exactly the failure that makes ad reporting say no campaign ever produced
anything. There is a test for it.

**Consent.** The cookie is written only while tracking is allowed. A visitor who declines,
or whose browser broadcasts Global Privacy Control, gets no cookie — and if they decline
after one was written, it is deleted immediately rather than left to expire. Attribution is
marketing measurement; it belongs under the same choice as GA4 and the Meta Pixel.

**What lands where:**

| Destination | What it gets |
|---|---|
| Supabase `public.leads` | 14 columns: `utm_*`, `click_id` + `click_id_type`, `landing_page`, `referrer`, `first_touch_*`, `touch_count` |
| DealerTide note | Plain-English lines the salesperson reads without leaving the record: `— Source (last touch): google / cpc / spring-doublewides` |
| Lead email (Resend) | A "Campaign" row |
| Google Sheets | An extra column |
| `/admin` → Leads | A "Came from" column: channel, campaign, first touch when it differs, landing page |
| `public.lead_attribution_report` | A view that resolves the channel, with `answer engine` broken out |

**Files:** `src/lib/attribution.ts` (the module), `src/components/AttributionTracker.tsx`
(client capture), `supabase/migrations/20260920_lead_attribution.sql` (columns, indexes,
view), plus wiring in `/api/leads`, `actions/leads.ts`, `leads-store.ts`, `admin-data.ts`
and `LeadsTable.tsx`. 16 tests in `tests/attribution.test.ts`.

> **The migration must be applied to Supabase BEFORE this deploys.** PostgREST rejects an
> insert naming an unknown column with a 400, which would take every website lead down
> until the migration landed. It is the first item on the checklist.

### S3 — offline conversion upload (the payoff, not yet built)

Storing `click_id` is the prerequisite for the thing that actually changes ad performance:
telling Google Ads and Meta which clicks became **sales**, not just which became leads. A
manufactured home has a long, offline close, so optimising bidding on form fills optimises
for the wrong thing — the cheap tyre-kicker lead wins.

The path, once there are enough closed sales to be worth it:

1. Add a `closed_at` and a `sale_value` column to `leads` (or reconcile from DealerTide).
2. A weekly job selects closed leads with a `click_id` from the last 90 days.
3. Upload to the Google Ads API (`ClickConversion` with `gclid`) and the Meta Conversions
   API (`fbclid` → `fbc`).
4. Switch the campaigns from "maximise leads" to "maximise conversion value".

Both platforms cap the lookback at 90 days, which is the same window the cookie uses.

### CRM / webhook patterns

The fan-out in `/api/leads` is already the right shape and worth stating as the house
pattern, because it is not obvious:

```ts
// Every channel runs concurrently; no single failure can block the response
// or lose the lead. The durable Supabase copy goes first.
const [storeResult, emailResult, sheetsResult, dtResult] = await Promise.allSettled([
  storeLead({ ...lead, attribution }),
  sendEmail({ ...lead, attribution: attributionText }),
  appendToSheet({ ...lead, attribution: attributionText }),
  pushLeadToDealertide({ ...lead, message: dtMessage }),
]);
```

`Promise.allSettled`, a durable write before any third party, per-channel logging, and a
Resend alert when the CRM of record rejects or de-dupes. Any new channel goes in that
array and inherits all of it.

One thing to add when there is time: **`/api/leads` has no application-level rate limit.**
`AGENTS.md` says that is a Vercel Firewall rule rather than code, which is a reasonable
division — but confirm the rule actually exists. Turnstile now covers form traffic; a
direct scripted POST that omits `hp` is still only limited at the platform edge.
